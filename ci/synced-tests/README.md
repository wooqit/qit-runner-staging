### Synced tests

This directory contains tests that are synced with WooCommerce Core.

We fetch tests from WooCommerce Core and save them here to be used by QIT.

### Choosing which Woo Core suite a run executes

Woo Core API and E2E tests have two separate update paths:

- **Synced test sources** are the WooCommerce Core test files copied into
  `ci/synced-tests/<test-type>-<woocommerce-version>`. Use the "Updating Synced
  Tests" process below when the Woo Core test sources or their Playwright setup
  need to be refreshed from the WooCommerce monorepo.
- **Published package versions** decide which Woo Core E2E suite a run executes.
  A test package version covers a whole WooCommerce `major.minor` and is two
  segments: `woocommerce/core-e2e-tests:11.0` is the spec set for WooCommerce
  11.0, so 11.0.0 and 11.0.1 both resolve to it. Publishing, retiring or
  republishing one of those is how the Woo Core E2E suite is rolled out and
  rolled back. No deploy is involved.

### Rolling out a Woo Core E2E suite

Publish the package version for the WooCommerce version it covers:

```bash
qit package:publish ci/tests/woo-e2e/test-package 11.0
```

Manager resolves each WooCommerce version it offers to the package version
published for its `major.minor`, and hands the CLI the answer in sync data under
`test_package_versions`. Every 11.0.x run picks it up on the CLI's next sync,
which is within a minute.

Nothing else covers it. A WooCommerce version with no package of its own runs
`latest` and says so, rather than the nearest older version, which would read as
a match while running specs written for another release. So publishing for a new
line is part of supporting it: the moment its prerelease is offered, every run on
that line is on the default until you do.

Verify with the sync payload rather than by reading code:

```bash
curl -s -X POST "https://<manager>/wp-json/cd/v1/cli/sync" | jq '.test_package_versions'
```

### Rolling back

Two levers, both without a deploy:

- **Republish the same version.** A package version is replaced in place, so
  `qit package:publish <path> 11.0` from a known-good tree restores it for every
  WooCommerce 11.0.x run at once. A run records the checksum of the artifact it
  executed, so runs before and after the republish stay distinguishable.
- **Retire the version.** `qit package:delete woocommerce/core-e2e-tests:11.0`
  marks it inactive, and resolution stops considering it: 11.0.x then falls to
  the fallback. Use this to withdraw a bad suite when there is no good tree to
  republish yet, knowing those runs move to the line in development.

**Never retire `latest`.** It is the fallback, and a QIT CLI released before
package versions existed asks for it by name for every Woo Core E2E run. The
download endpoint answers 404 for an inactive package, so retiring it breaks
those runs outright. Republish it instead.

`default_test_packages` in
`plugins/cd-manager/src/REST/V1/Endpoints/CLI/SyncEndpoint.php` is **no longer
the rollout control point for Woo Core E2E**. It is the fallback used when no
published package version covers the WooCommerce version a run asked for, so
editing it cannot roll back a version that already resolves to an active
package. It is still the control point for `performance`, and for `api` until
`core-api-tests` gets published versions of its own.

Do not edit the `package` field in the Core package manifests under
`ci/tests/woo-api/test-package/qit-test.json` or
`ci/tests/woo-e2e/test-package/qit-test.json` to change versions. Those
manifests name the package; the version is the one given to
`qit package:publish`.

### Manually patching Woo Core test packages

The package source under `ci/tests/woo-api/test-package` and
`ci/tests/woo-e2e/test-package` is manually maintained. It is not regenerated by
`ci/update-tests.php`, and it does not currently have the same direct sync or
patch flow that `ci/synced-tests` has.

Use this path when a Woo Core API/E2E package issue is reported and the fix
cannot wait for a larger migration of the Core tests into test packages.

Recommended process:

1. Reproduce or inspect the failing run, then identify the exact package and
   test file. Confirm whether the failure is a QIT environment mismatch, a
   flaky selector/timing issue, or a Woo Core test behavior that changed
   upstream.
2. Check WooCommerce Core for an existing issue or PR. If an upstream fix exists,
   backport the smallest useful change and link the Woo issue/PR in the Manager
   PR. If no upstream fix exists, keep the QIT change narrowly scoped and explain
   why it is QIT-specific.
3. Patch the bundled package source directly:

   - Woo API: `ci/tests/woo-api/test-package/tests/api-tests/...`
   - Woo E2E: `ci/tests/woo-e2e/test-package/tests/...`
   - Shared helpers or utilities: the matching file under the same
     `test-package` directory.

4. If the E2E fix touches bundled `@woocommerce/e2e-utils-playwright` files,
   commit the source and built outputs together. That package is checked in
   prebuilt, so changes under `src/` must stay aligned with `build/` and
   `build-module/`.
5. If the package dependencies change, update both `package.json` and
   `package-lock.json` in the affected test package.
6. Check whether the same failure exists in synced tests. If it does, patch the
   synced path too, or add a `ci/ci.sh` rule / `ci/patches` entry so the fix is
   preserved the next time synced tests are regenerated.
7. Smoke-test the package against staging before making it the default. When
   possible, test the local package path first; otherwise publish a staging
   package version and run a focused Woo API/E2E test with the affected extension.
8. Publish the package version covering the WooCommerce version the fix is for,
   e.g. `qit package:publish ci/tests/woo-e2e/test-package 11.0`. That replaces
   it in place for every run on that WooCommerce version; see "Rolling out" and
   "Rolling back" above. No `SyncEndpoint.php` edit and no deploy is involved
   for Woo Core E2E.

PRs for manual patches should include:

- The failing QIT run or issue that triggered the patch.
- The upstream WooCommerce issue/PR/commit when one exists.
- Whether the change is a backport, a QIT-specific hardening, or a temporary
  skip.
- Whether the fix was applied to the synced tests, the test-package source, or
  both.

### Woo Core change alerts

The `Woo Core Test Watch` GitHub Actions workflow checks WooCommerce Core
`trunk` daily for changes to files that commonly affect QIT's synced tests or
manually maintained Woo API/E2E test packages. The watched paths are defined in
`.github/woo-core-test-watch.json`.

When watched files change, the workflow creates or updates a single tracking
issue named `Woo Core test-impacting changes detected`. Use that issue to decide
whether to run the synced-tests update, patch a bundled test package, publish a
new package version, or take no action.

After the changes are reviewed, update `.github/woo-core-test-watch-baseline`
to the WooCommerce head SHA shown in the tracking issue. That marks the upstream
range as reviewed and prevents the workflow from reporting the same files again.

### Updating Synced Tests

To update the tests, do the following steps:

#### API Tests

- Create a new branch
- Open a terminal in the `ci` folder
- Run `php update-tests.php`
- Don't run the self-tests when updating (select `N` when the script asks)
- Deploy the manager to staging and switch your CLI to staging (`env:switch staging` or `switch staging`, depending on your CLi version)
- In the QIT CLI folder, go to the `_tests/managed_tests` and update the snapshots for the Woo API tests, first `php QITSelfTests.php update woo-api`. Note: if you run into any issues, make sure to run `composer install` in the `_tests/managed_tests` directory first.
- Commit the resulting changes and open a PR
- Review the changes for any odd changes (see the Tips below)

Note: if you run into any errors when pushing, you may need to update your git config postBuffer:

```
git config --global http.postBuffer 157286400
```

On the PR, we expect to see the following changes:

- Older tests will be removed
- New tests will be added
- The file `plugins/cd/manager/synced-with-woo.txt` will have changed to reflect that
- The delete products tests (both for the API and e2e tests) are expected to fail when updating snapshots, so these changes can be ignored.
- The no-op tests should succeed, if there's any failures we need to review those.

#### E2E Tests

- If everything is well with API, run the E2E as well with `php QITSelfTests.php update woo-e2e` and commit their snapshot as well
- This will take up to 45 minutes, and it's expected that the first run will fail, you can investigate the failures and skip them:
- Pick a "no-op" test snapshot and use it as a reference for skipping tests.

To skip a test, edit the file `ci/ci.sh` and scroll to the section that has the skips, it looks like this:

```bash
if [ "${QIT_TEST_TYPE}" == "woo-e2e" ]; then
  # Skips that applies to all versions:
  php ./bin/search-replace.php "${TEST_DIR}/playwright.config.js" "video: 'on-first-retry'" "video: 'retain-on-failure'"

  # Skips that applies for only specific versions:

  # 8.7
  if version_compare "$QIT_WOOCOMMERCE_TAG" "8.6.999" ">" && version_compare "$QIT_WOOCOMMERCE_TAG" "8.7.999" "<"; then
    php ./bin/search-replace.php "${TEST_DIR}/tests/merchant/order-emails.spec.js" "test( 'can receive completed email'" "test.skip( 'can receive completed email'"

    # Ported from 8.6
    php ./bin/search-replace.php "${TEST_DIR}/tests/merchant/order-refund.spec.js" "test( 'can issue a refund by quantity'" "test.skip( 'can issue a refund by quantity'"
  fi
fi
```

What to skip:
- On our tests, we are not interested in covering Woo Core behavior per-se, we leave that to Woo E2E. What we are interested in is running as much Woo E2E tests possible with other extensions active. Some tests don't work on our environment, so we skip them
- On the no-op snapshot, tests that were previously "pending" and now are "failed" are tests that we skipped in the previous version, and that continues to fail, so we should skip them, eg:

![image](https://github.com/Automattic/compatibility-dashboard/assets/9341686/8acd13fa-0fa8-4d02-b945-41202dba6083)

To skip that test, we would create a new version compare block and put the skips inside of it.

If you have GitHub CoPilot, you can copy and paste the test file and assertion in a comment, like this:

```
# merchant\\/create-shipping-zones.spec.js allows customer to benefit from a free Free shipping if in BC
```

And start filling the next line so that it auto-completes it for you based on the surrouding skips:

```
# merchant\\/create-shipping-zones.spec.js allows customer to benefit from a free Free shipping if in BC
php <tab>

// Will become:
php ./bin/search-replace.php "${TEST_DIR}/tests/merchant/create-shipping-zones.spec.js" "test( 'allows customer to benefit from a free Free shipping if in BC'" "test.skip( 'allows customer to benefit from a free Free shipping if in BC'"
```

Then you just delete the comment that you used to generate it and commit the skip.

Do this until there are no more tests failing on the `no-op`, at which point you can run just one more to make sure. If there is a flaky test that fails intermitently, feel free to skip it as well.

#### Manual patches

We have one manual patch we apply:

```javascript
page.on('dialog', async (dialog) => {
    console.log(`Dismissing dialog: ${dialog.message()}`);
    await dialog.accept();
});
```

Add this to the `userDeletionTest` just before `await page.getByRole( 'link', { name: 'Delete' } ).click();`

See https://github.com/Automattic/compatibility-dashboard/pull/1442 for more context.

### Testing non-synced tests

- Spin up the QIT CLI repository locally
- Edit the self test environments to use the new version, eg: `_tests/api/main/env.php` file, change the `woocommerce_version` there.
- Point your local QIT CLI repo to staging with `qit switch staging`
- Deploy the Manager with the new tests to Staging
- Run the self-tests with `php QITSelfTests.php update`. Note: This will take up to one hour because of the synced E2E tests, otherwise it would be something like 5 minutes.
